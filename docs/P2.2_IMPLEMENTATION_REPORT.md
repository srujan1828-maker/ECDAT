# ECDAT V4 — P2.2 Crypto-Agility Intelligence Implementation Report
## Research-Grade Evidence-Driven Cryptographic Agility Engine

### Executive Summary

Phase P2.2 delivers the **Crypto-Agility Intelligence Engine** for ECDAT V4, addressing the research question:
> *"Can crypto-agility be measured from observable architectural and implementation evidence rather than from a manually assigned score?"*

The system rejects opaque, black-box scalar score generation in favor of a rigorous, 7-dimensional categorical evaluation model (`SUPPORTED`, `OBSERVED`, `PARTIALLY_OBSERVED`, `CONSTRAINED`, `BLOCKED`, `UNKNOWN`, `NOT_APPLICABLE`, `SCANNER_UNAVAILABLE`), accompanied by a comprehensive `CryptoChangeSurface` analysis and full reason-chain explainability.

All existing legacy functionality in `backend/engine/agility_engine.py` and `POST /api/agility/evaluate` remains 100% backward compatible and untouched.

### 3. Architecture & Delivered Modules

#### A. Core Engine (`backend/engine/agility/`)
- `models.py`: Strongly typed dataclasses and enums (`AgilityDimension`, `AgilityState`, `AgilityConfidence`, `ChangeComplexity`, `CryptoChangeSurface`, `AgilityAssessment`).
- `evidence.py`: Evidence adapter normalizing P0/P1 observations, handling hyphen/underscore token variations and confidence mapping.
- `rules_engine.py`: Deterministic YAML rule evaluator against `crypto_agility_rules.yaml`.
- `dimensions/`:
  - `algorithm_agility.py`: Provider abstraction detection vs direct primitive invocations.
  - `configuration_agility.py`: Dynamic env vars / config files vs hardcoded keys.
  - `dependency_agility.py`: Dynamic shared libraries vs static in-tree dependencies.
  - `protocol_agility.py`: Dynamic protocol negotiation vs fixed cipher suites.
  - `certificate_agility.py`: Automated ACME rotation vs embedded static certs/keys.
  - `deployment_agility.py`: Containerization & dynamic reload vs immutable bare-metal/firmware.
  - `validation_agility.py`: Wycheproof / KAT / test vectors vs absent test suites.
- `change_surface.py`: Blast radius traversal, footprint extraction, and complexity calculation.
- `explainability.py`: Reason chain builder and audit provenance generator.
- `agility_pipeline.py`: Pipeline coordinator, unweighted applicable score derivation, and database persistence.

#### B. Knowledge Base (`backend/knowledge/`)
- `crypto_agility_rules.yaml`: Frozen version `2024.1` with deterministic criteria for all 7 dimensions (`AGL-ALG-*`, `AGL-CFG-*`, `AGL-DEP-*`, `AGL-PRT-*`, `AGL-CRT-*`, `AGL-DPL-*`, `AGL-VAL-*`).

#### C. Database Persistence (`backend/engine/asset_graph.py` & `scan_store.py`)
- Added `agility_assessments` and `change_surfaces` tables in SQLite schema with indexed `asset_id` and `scan_id`.
- Non-overwriting historical retention with UUID primary keys.
- Implemented query helpers `save_agility_assessment`, `get_agility_assessment`, `save_change_surface`, `get_change_surface`.

#### D. API Endpoints (`backend/main.py`)
- `GET /api/assets/{asset_id}/agility`: Retrieve latest multi-dimensional agility assessment.
- `GET /api/assets/{asset_id}/agility/why`: Explainability report with firing rules and evidence links.
- `GET /api/assets/{asset_id}/change-surface`: Detailed change footprint and blast radius analysis.
- `POST /api/agility/evaluate-v2`: Ad-hoc multi-dimensional evaluation payload.
- `POST /api/agility/evaluate`: Legacy endpoint untouched and backward compatible.

The engine satisfies all 40 required semantic axioms:
- **Axioms 1–4**: Hardcoded API is not configurable; config option is not runtime replacement; abstraction is not migration completion; dependency pin is not immutable dependency.
- **Axioms 5–8**: Graph centrality $\ne$ agility; graph centrality $\ne$ risk; high risk $\ne$ low agility; high risk $\ne$ high agility.

### 5. Defects Found and Fixed During Audit

#### Defect 1: Cross-Dimension Scanner Unavailability Pollution
- **Severity**: Moderate (Functional Isolation)
- **Root Cause**: All 7 dimension modules evaluated `if context.get("scanner_unavailable") or any("SCANNER_UNAVAILABLE" in e.state for e in evidence_items):`. Because `evidence_items` is passed as a unified list of all evidence collected for the asset, a scanner failure on one dimension (e.g. network probe timeout) caused all other dimensions (including source/algorithm AST where valid evidence existed) to incorrectly report `SCANNER_UNAVAILABLE`.
- **Files Modified**:
  - `backend/engine/agility/evidence.py`: Added `is_dimension_scanner_unavailable(dimension, evidence_items, context)` filtering by dimension-specific observation types and keywords.
  - `backend/engine/agility/dimensions/algorithm_agility.py`
  - `backend/engine/agility/dimensions/configuration_agility.py`
  - `backend/engine/agility/dimensions/dependency_agility.py`
  - `backend/engine/agility/dimensions/protocol_agility.py`
  - `backend/engine/agility/dimensions/certificate_agility.py`
  - `backend/engine/agility/dimensions/deployment_agility.py`
  - `backend/engine/agility/dimensions/validation_agility.py`
  - `backend/engine/agility/agility_pipeline.py`: Added check ensuring `overall_state = AgilityState.SCANNER_UNAVAILABLE` when all active dimensions are scanner unavailable.
- **Regression Test**: Added `TestCompositeScoreAxioms::test_score_scanner_unavailable_dimension_excluded` and `test_score_zero_applicable_dimensions_returns_none` in `backend/tests/test_p22_agility_adversarial.py`.
