## 4. Concrete Defect Log

During this hardening audit, two architectural defects and two precision issues were identified, documented, and repaired:

### Defect 1: Evidence Monotonicity Inversion in Asset Graph
- **Root Cause**: `AssetGraphService.update_asset` unconditionally updated `highest_evidence_level` and `confidence` when provided in `kwargs`. If a high-level observation ($E3$ or $E4$) was previously recorded for an asset, a subsequent scan finding a low-level candidate ($E1$ string match) downgraded the asset's recorded evidence level.
- **Fix**: Implemented rank-based comparison (`curr_rank = int(curr_level[1])`) in `backend/engine/asset_graph.py`. If `curr_rank > new_rank`, the existing higher evidence level is retained. Similarly, `confidence = max(existing.confidence, new_confidence)` prevents confidence degradation.
- **Regression Test**: `test_asset_graph_monotonicity_protection` in `backend/tests/test_p1_binary_hardening.py`.
- **Verification**: Updating an $E3$ asset with an $E1$ observation confirms `highest_evidence_level == "E3"` and confidence is maintained at 0.88. Subsequent update with $E4$ successfully upgrades the asset.

### Defect 2: Orphaned Extracted Firmware Artifacts (Missing Child Provenance)
- **Root Cause**: `FirmwareExtractor` unpacked recursive archive members (`ExtractedMember`) but did not record the SHA-256 hash of the parent container or the extraction method. Downstream pipelines could not construct cryptographic provenance chains connecting extracted child binaries back to the root firmware image.
- **Fix**: Added `parent_hash: str`, `container_path: str`, and `extraction_method: str` to `ExtractedMember` in `backend/engine/binary/firmware_extractor.py`. Propagated parent container hashes and virtual container paths across nested extractions.
- **Regression Test**: `test_firmware_child_provenance_chain` and `test_firmware_graph_containment_edges`.
- **Verification**: Child binaries extracted from nested archives retain the exact SHA-256 hash of the enclosing archive and establish `RelationshipType.CONTAINS` edges in the relational AssetGraph.

### Defect 3: Premature Cryptographic Parameter Normalization Collapse
- **Root Cause**: `BinaryNormalizer.normalize_algorithm` collapsed distinct security levels and modes into generic family names (`"RSA_2048"` $\to$ `"RSA"`, `"crystals_kyber768"` $\to$ `"ML-KEM"`, `"aes_256_gcm"` $\to$ `"AES"`).
- **Fix**: Added `normalize_canonical(raw_name, preserve_specificity=True)` and `normalize_entity(raw_name)` to `backend/engine/binary/binary_normalizer.py`. Mode extraction (`infer_mode`) and key-size extraction (`infer_key_size`) preserve parameter specificity when available, while preserving backward compatibility for existing callers.
- **Regression Test**: `test_normalization_canonical_specificity_preservation` and `test_normalization_entity_audit`.
- **Verification**: `RSA_2048` normalizes to `RSA-2048`, `crystals_kyber768` to `ML-KEM-768`, and `aes_256_gcm` to `AES-256-GCM`.

### Defect 4: Unbounded Ghidra/angr Evidence State Drift
- **Root Cause**: External reverse-engineering findings did not have a dedicated evidence constructor in `BinaryEvidenceGenerator`, leaving open the possibility of external tools falsely asserting dynamic execution ($E5$).
- **Fix**: Implemented `BinaryEvidenceGenerator.from_deep_re_finding` enforcing strict mapping: Ghidra $\to E3$, angr $\to E4$, YARA $\to E1$, with `state=EvidenceState.MEASURED` and explicit non-execution epistemic limitations.
- **Regression Test**: `test_deep_re_evidence_mapping_epistemic_separation`.
- **Verification**: Confirmed all deep RE findings produce $E1..E4$ evidence with state `MEASURED`, strictly forbidding $E5$.

## 5. Binary Identification & Triage Audit

`BinaryIdentifier` performs non-destructive format triage using fixed-size byte inspection:
- **ELF**: Detects `\x7fELF`, inspects byte 4 (`EI_CLASS` for 32/64-bit), byte 5 (`EI_DATA` for little/big endian), and byte 18 (`e_machine` for x86, x86_64, ARM, AArch64, MIPS, RISC-V).
- **PE**: Detects `MZ` signature at offset 0, follows `e_lfanew` pointer, verifies `PE\0\0` signature at offset $\le 1024$, and parses Machine architecture and characteristics.
- **Mach-O**: Detects 32-bit (`0xFEEDFACE`, `0xCEFAEDFE`), 64-bit (`0xFEEDFACF`, `0xCFFAEDFE`), and Universal FAT (`0xCAFEBABE`, `0xBEBAFECA`).
- **Firmware Containers**: Detects U-Boot uImage (`0x27051956`), FIT DTB (`0xD00DFEED`), CPIO new ASCII (`070701`), and SquashFS (`hsqs`, `sqsh`).
- **Archive Streams**: Detects ZIP (`PK\x03\x04`), Gzip (`\x1F\x8B`), and Tar (POSIX `ustar` magic at offset 257).
- **Handling of Truncated & Corrupted Data**: Buffers smaller than required magic lengths are safely classified as `BinaryFormat.UNKNOWN` without throwing exceptions.

## 7. Mach-O Reality Assessment

To prevent false capability claims regarding Apple Mach-O binaries:
1. **What is genuinely supported**:
   - Binary format identification: 32-bit, 64-bit, and Universal/Fat headers are recognized (`BinaryFormat.MACHO`).
   - Architecture classification: x86_64 and ARM64 slices are detected.
   - Load command iteration: `LC_SEGMENT_64` segments and section headers (`__TEXT`, `__cstring`, `__const`) are parsed.
   - Dynamic library imports: `LC_LOAD_DYLIB` load commands are parsed, extracting linked dylibs (e.g. `libcrypto.dylib`, `libSystem.B.dylib`).
2. **What is unsupported**:
   - Pure-Python `nlist` symbol table and two-level namespace symbol resolution are unsupported.
   - Objective-C and Swift metadata recovery are unsupported in native parsing.
   - Mach-O deep disassembly is unavailable without external Ghidra/angr engines.

## 8. Symbol Analysis Hardening

`BinarySymbolParser` reads static (`.symtab`) and dynamic (`.dynsym`) symbol tables:
- **Defined vs. Imported External Symbol Semantics**:
  - Defined symbols (`is_defined=True`): Have a non-zero section index (`shndx != SHN_UNDEF`). Mapped to **$E3$ BINARY_SYMBOL** evidence with confidence $0.90$.
  - Imported symbols (`is_defined=False`): Have `shndx == SHN_UNDEF`. Mapped to **$E2$ BINARY_SYMBOL** evidence with confidence $0.80$.
- **Adversarial Assertion**: Imported symbols include the explicit limitation:
  `"Dynamic reachability or runtime invocation path is not proven without dynamic tracing."`
- **Knowledge Base Coverage**:
  - PQC: `ML-KEM` (`kyber`, `oqs_kem_kyber`), `ML-DSA` (`dilithium`), `SLH-DSA` (`sphincs`), `Falcon`.
  - Classic Asymmetric: `RSA` (`rsa_generate`, `rsa_sign`), `ECDSA` (`ecdsa_do_sign`), `ECDH` (`ecdh_compute_key`, `x25519`).
  - Symmetric: `AES` (`AES_set_encrypt_key`, `AES_encrypt`), `3DES`, `ChaCha20`, `SM4`.
  - Hashes: `SHA-256`, `SHA-512`, `SHA-3`, `BLAKE2`, `MD5`, `SHA-1`.

## 9. Import & Dynamic Linking Hardening

`BinaryImportParser` parses dynamic dependencies:
- **ELF**: Traverses `.dynamic` section entries, resolving `DT_NEEDED` offsets against `.dynstr`.
- **PE**: Reads the Data Directory Import Table (RVA 1), maps RVAs to section file offsets, and extracts DLL names from `IMAGE_IMPORT_DESCRIPTOR` structures.
- **Mach-O**: Scans load commands for `LC_LOAD_DYLIB` (`0x0C` / `0x8000000C`) and unpacks library path strings.
- **Classification & Limitations**:
  - Windows libraries: `bcrypt.dll` (CNG), `crypt32.dll` (CryptoAPI), `ncrypt.dll`.
  - Unix libraries: `libcrypto.so`, `libssl.so`, `libsodium.so`, `libgnutls.so`, `libwolfssl.so`, `libmbedcrypto.so`, `liboqs.so`.
  - Limitation Guarantee: All imported library evidence records:
    `"Binary links against shared cryptographic library. Specific algorithms used at runtime cannot be confirmed from dependency declaration alone."`

## 11. Endianness & Word-Order Permutation Audit

To detect constants compiled on architectures with differing endianness or word packing:
- `BinarySignatureMatcher` supports `supports_word_reversal: true`.
- When set, for any signature whose length is a multiple of 4 bytes, a 32-bit word-reversed permutation is computed:
  $$\text{Reversed}(B) = \bigoplus_{i=0}^{N/4 - 1} B[4i \dots 4i+3]^R$$
- **Empirical Test**: SHA-256 initialization vector (`6a09e667bb67ae85...`) compiled with reversed word order (`67e6096a85ae67bb...`) was matched with `byte_order: "reversed-word-order"` (Confidence: 0.90).

## 14. Secret Detection & Masking Security

Embedded cryptographic secrets are handled under strict confidentiality controls:
- **Zero Raw Byte Leakage Guarantee**:
  - Private key payload lines are never emitted to log outputs, evidence descriptions, or graph attributes.
  - All private keys are masked as `SECRET_INDICATOR_DETECTED`.
- **Audited Secret Types**:
  - RSA Private Key: Detected, validated (`is_valid_pem=True`), key size (2048/4096 bits) extracted, masked.
  - EC Private Key: Detected, validated, curve/key size (256/384 bits) extracted, masked.
  - Encrypted Private Key: Flagged with `is_encrypted=True`, masked.
  - X.509 Certificate: Distinguished from private keys, recorded as `ObservationType.X509_CERTIFICATE`.
  - Non-PEM Base64: Random base64 strings without valid PEM delimiters are rejected (`test_secret_random_base64_rejection`).

## 18. Evidence Semantics & Level Audit

Evidence items generated by `BinaryEvidenceGenerator` adhere to strict levels and states:
- **E1 (Pattern / Heuristic Candidate)**: String literals and YARA pattern matches (`ObservationType.BINARY_REFERENCE`, `ObservationType.BINARY_SIGNATURE`).
- **E2 (Structured Asset / Signature / Import)**: Byte constants in sections, ASN.1 OIDs, imported undefined symbols, and dynamic library dependencies (`ObservationType.BINARY_REFERENCE`, `ObservationType.BINARY_SYMBOL`).
- **E3 (Confirmed Function / Key Material)**: Compiled defined functions in `.text`, validated embedded PEM private keys (`ObservationType.BINARY_FUNCTION`, `ObservationType.HARDCODED_KEY`).
- **E4 (Symbolic Reachability)**: angr data-flow / control-flow reachability analysis.
- **E5 (Live Execution)**: **NEVER GENERATED BY BINARY STATIC SCANNER**. Static and symbolic analysis cannot observe live protocol negotiation.
- **Evidence State**: Always `EvidenceState.MEASURED`, never ungrounded.
