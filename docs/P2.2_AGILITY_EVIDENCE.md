# ECDAT V4 — P2.2 Agility Evidence & Normalization
## Observation Mapping, Signal Vocabulary, and Evidence Discipline

### 1. Evidence Adapter Architecture

The agility engine ingests heterogeneous findings emitted by upstream scanners:
- Source code AST parses (`SOURCE_API_USE`, `SOURCE_DECLARATION`)
- Dependency manifests and lockfiles (`DEPENDENCY_DECLARATION`, `DEPENDENCY_LOCKFILE`)
- Binary disassemblies and symbols (`BINARY_SYMBOL`, `BINARY_STRING`, `FIRMWARE_CONTENT`)
- Network TLS probes (`TLS_NEGOTIATION`, `TLS_EXTENSION`, `PROTOCOL_CONFIGURATION`)
- Certificate inspections (`X509_CERTIFICATE`, `ROTATION_MECHANISM`, `HARDCODED_KEY`)
- Test and build execution logs (`CRYPTO_TEST`, `TEST_DECLARATION`)

The `AgilityEvidenceItem` adapter (`backend/engine/agility/evidence.py`) normalizes these raw findings into standardized items containing:
- `id`: Unique evidence identifier.
- `observation_type`: Standardized observation category.
- `level`: Evidential hierarchy tier ($E0$–$E5$).
- `state`: Evidence fusion status (`MEASURED`, `CORROBORATED`, `INFERRED`, `CONTRADICTORY`).
- `source`: Collector name or analyzer subsystem.
- `file_path` / `symbol_name` / `line_number`: Ground-truth location pointers.
- `data`: Arbitrary structured dictionary containing raw parser outputs.

---

### 2. Signal Normalization & Keyword Matching

Evidence text often contains descriptive phrases or tokenized identifiers (e.g. `"automated certificate rotation"` vs `"automated_rotation"`, `"provider_abstraction"` vs `"provider abstraction"`).

`AgilityEvidenceItem.has_text(*keywords)` handles robust text matching:
1. Normalizes all underscores (`_`) and hyphens (`-`) into single spaces.
2. Performs case-insensitive matching across:
   - Evidence description
   - Direct string representations
   - Structured `data` dictionary keys and string values
3. Allows exact symbol and phrase corroboration without brittle literal syntax dependencies.

### 3. Evidential Principles & Non-Fabrication Invariants

#### Axiom A: Syntactic Indicators Do Not Imply Operational Capability
- A static string reference to `"TLSv1.3"` in an application binary does **not** prove TLS 1.3 is negotiated.
- An import statement `import org.bouncycastle.pqc` does **not** prove post-quantum cryptography is actively used.
- An OCSP extension present in an X.509 certificate does **not** prove revocation checks are enforced by the client.

#### Axiom B: Absence of Evidence Is Distinct From Negative Evidence
- If no cryptographic tests are found in a scan manifest, validation agility is `UNKNOWN`, **never** `BLOCKED`.
- It only evaluates to `BLOCKED` or `CONSTRAINED` if an explicit negative measurement is corroborated (e.g. `observation_type: "TEST_DECLARATION"` with description `no_tests_observed` and context `has_crypto_tests: False`).

#### Axiom C: Tool and Environment Failures Must Be Preserved
- If an automated probe fails because of network timeouts, firewall drops, or Windows Defender EDR process termination, the evidence must record `state: "FAILED"` or `error: "scanner_unavailable"`.
- The corresponding dimension evaluates strictly to `SCANNER_UNAVAILABLE`. The engine **never** downgrades an asset's agility score because a scanning tool encountered an environment error.

#### Axiom D: Contradictory Evidence Preservation
- When two scanners report conflicting information (e.g. static analysis flags `hardcoded_key` while network scan observes `acme_rotation`), both evidence items are preserved in the dimensional reason chain.
- The state evaluates to `PARTIALLY_OBSERVED` with an explicit reason bullet indicating conflicting signals, rather than discarding one or silently averaging them.
