# ECDAT V4 P2.3 — Blast Radius Intelligence Architecture

## 1. Architectural Mission & Scope
Phase P2.3 implements the **Blast Radius Intelligence Engine** for ECDAT V4, answering the foundational operational security question:
> *"If this cryptographic asset, algorithm, library, certificate, protocol, dependency, configuration, or implementation changes, what other assets may be affected?"*

Blast radius is strictly an impact analysis and reachability layer built upon the existing, persistent Crypto Asset Graph.

```
       [ Upstream Callers / Applications / Deployments ]
                             ^
                             |  Reverse Traversal (Incoming Edges)
                             |  (USES, DEPENDS_ON, IMPLEMENTS, PROTECTS, SERVES)
                             |
             [ Target Cryptographic Asset ]
                  (e.g., RSA-1024 / OpenSSL 1.0.2)
```

---

## 2. Core Architectural Principles & Invariants

### 2.1 Single Authoritative Crypto Asset Graph
ECDAT V4 maintains exactly **one** persistent graph persistence model in SQLite (`crypto_assets`, `graph_edges`, `evidence`). P2.3 does NOT build a second parallel graph or external graph DB. Traversal reuses `AssetGraphService.get_blast_radius` and enhances it with typed `DependencyPath` sequences, cycle safety, depth/breadth limits, and evidence correlation.

### 2.2 Strict Orthogonality
Blast Radius is mathematically and conceptually orthogonal to:
- **Cryptographic Risk** (P2.1): A deprecated cipher with 0 callers has high risk, but zero blast radius.
- **Crypto-Agility** (P2.2): An agile algorithm can still have widespread blast radius if 20 microservices consume it.
- **Migration Priority**: Prioritization happens in the migration planning engine, not inside topological reachability.
- **Graph Centrality**: Pure PageRank or Betweenness centrality does not equate to operational criticality.

There is **no blended score**. The engine outputs categorical states and structured paths, leaving numerical composite scores decoupled.

## 3. Traversal Engine & Safety Bounds
To guarantee stability against cyclic graphs and dense clusters, `BoundedGraphAnalyzer` enforces strict bounds:
- `DEFAULT_MAX_DEPTH = 10`: Traversal halts along any path exceeding depth 10, tagging `MAX_DEPTH_REACHED`.
- `DEFAULT_MAX_PATHS = 100`: Path fan-out is truncated at 100 paths, tagging `MAX_PATHS_REACHED`.
- `DEFAULT_MAX_NODES = 500`: Node expansion stops at 500 nodes, tagging `MAX_NODES_REACHED`.
- `DEFAULT_MAX_EDGES = 1000`: Edge traversal stops at 1000 edges, tagging `MAX_EDGES_REACHED`.
- `Cycle Pruning`: Branch-local visited sets detect cyclic loops (`A -> B -> C -> A`), prune the cyclic branch, and flag `CYCLE_DETECTED_AND_PRUNED`.
- Whenever a bound is triggered, `partial_result: true` is set on the assessment.

## 4. Subsystem Layout
- `backend/knowledge/blast_radius_rules.yaml`: Rule definitions (`BLST-REL-*`, `BLST-PTH-*`, `BLST-IMP-*`, `BLST-CRT-*`).
- `backend/engine/blast_radius/models.py`: Strongly typed dataclasses and categorical enums.
- `backend/engine/blast_radius/normalizer.py`: Edge/node normalization and deterministic SHA-256 graph hashing.
- `backend/engine/blast_radius/dependency_paths.py`: Path builder, length calculator, and multi-path detector.
- `backend/engine/blast_radius/graph_analyzer.py`: Bounded reverse DFS/BFS traversal engine.
- `backend/engine/blast_radius/criticality.py`: Evidence-backed architectural criticality assessment.
- `backend/engine/blast_radius/impact_classifier.py`: Categorical state and impact category classifier.
- `backend/engine/blast_radius/evidence.py`: Evidence correlation and contradiction detection.
- `backend/engine/blast_radius/explainability.py`: Audit reason chains and explainability report builder.
- `backend/engine/blast_radius/blast_radius_pipeline.py`: Master evaluation pipeline.
