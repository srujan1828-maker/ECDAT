# ECDAT V4 — P2.2 Cryptographic Change Surface
## Footprint Extraction, Blast Radius Integration, and Change Complexity

### 1. The Need for Change Surface Analysis
A cryptographic algorithm or protocol replacement is never an isolated operation. Migrating an algorithm (e.g. from RSA-2048 to ML-KEM-768 or Dilithium) impacts:
- Call sites and source files.
- Configuration manifests and environment variables.
- Direct and transitive package dependencies.
- Network endpoints and exposed port listeners.
- X.509 certificates and key stores.
- Upstream and downstream consuming services across the dependency graph.

The `CryptoChangeSurface` (`backend/engine/agility/models.py`) quantifies the exact architectural blast radius and change footprint before migration work begins.

---

### 2. Change Surface Schema

```python
@dataclass
class CryptoChangeSurface:
    asset_id: str
    affected_files: List[str]
    affected_modules: List[str]
    call_sites_count: int
    direct_dependencies: List[str]
    affected_protocols: List[str]
    affected_certificates: List[str]
    affected_endpoints: List[str]
    blast_radius_assets: List[str]
    blast_radius_count: int
    change_complexity: ChangeComplexity  # LOW, MODERATE, HIGH, VERY_HIGH
    summary: str
```

---

### 3. Blast Radius Integration

P2.2 reuses the graph traversal algorithms implemented in `AssetGraphService.get_blast_radius()`:
- Traverses incoming and outgoing dependency edges (`CALLS`, `USES`, `DEPENDS_ON`, `BINDS_TO`).
- Calculates the multi-hop transitive closure of all impacted services, modules, and hardware assets.
- Feeds `total_impacted_count` and `impacted_assets` directly into the change surface model without recalculating graph connectivity from scratch.

---

### 4. Change Complexity Evaluation

The change complexity reflects the technical friction required to execute a cryptographic transition:

| Complexity Level | Typical Criteria |
| :--- | :--- |
| `LOW` | High agility in algorithm & configuration; call sites $\le 3$; blast radius $\le 2$; zero hardcoded keys. |
| `MODERATE` | Modular architecture; call sites $4$–$10$; blast radius $3$–$10$; configuration updates required. |
| `HIGH` | Pinned dependencies or embedded keys; call sites $> 10$; blast radius $> 10$; firmware or legacy APIs. |
| `VERY_HIGH` | Hardcoded primitives; static ROM / un-updatable firmware; massive blast radius across multiple critical systems. |

**Important Distinction**:
Complexity measures **migration effort and operational risk**, not agility itself. A service can be architecturally agile (e.g., provider-abstracted) but have high complexity due to massive graph centrality (used by 50 microservices). P2.2 models these as distinct properties.
