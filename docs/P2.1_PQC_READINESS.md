# ECDAT V4 — P2.1 Post-Quantum Cryptographic Readiness Engine
## Multi-Role State Machine and Hybrid Cryptography Semantics

### 1. Conceptual Framework
PQC readiness cannot be represented as a single binary boolean flag. Real-world systems migrate cryptosystems across distinct functional roles independently:
1. **Key Establishment (`key_establishment`)**
2. **Digital Signatures (`signature`)**
3. **Public Key Infrastructure / Certificates (`certificate`)**
4. **Transport Protocols (`protocol`)**
5. **Cryptographic Libraries (`library`)**
6. **Application Logic (`application`)**

A system may negotiate hybrid post-quantum key establishment (`X25519MLKEM768`) while authenticating with a classical RSA-2048 certificate. Labeling this system "PQC Ready" or "Classical" would be factually incorrect. ECDAT V4 tracks readiness across each role independently.

---

### 2. Readiness State Taxonomy (`PQCReadinessState`)

| State | Definition | Example Evidence |
| :--- | :--- | :--- |
| `CLASSICAL_ONLY` | Purely classical cryptography with no PQC capability observed | Classical TLS 1.2 RSA handshake |
| `PQC_CAPABLE` | Software contains PQC code/algorithms, but runtime negotiation is unverified | Dependency on `liboqs` or `bouncycastle-pqc` |
| `PQC_ADVERTISED` | Server advertises PQC algorithm in negotiation options (e.g. SSH KEXINIT) | SSH server offers `sntrup761x25519-sha512@openssh.com` |
| `PQC_OFFERED` | Client offered PQC capability in handshake (e.g. TLS ClientHello) | Client offers hybrid named group |
| `HYBRID_NEGOTIATED` | Key establishment successfully completed combining classical + PQC primitives | TLS 1.3 handshake with `X25519MLKEM768` |
| `PQC_NEGOTIATED` | Key establishment or signature successfully completed using pure PQC | ML-KEM-768 or ML-DSA-65 negotiated |
| `PQC_ONLY` | Architecture enforces PQC exclusively, disallowing classical fallbacks | High-assurance quantum-only tunnel |
| `SCANNER_UNAVAILABLE` | Assessment could not probe the endpoint (timeout, connection refused) | Scanner failure (never marked clean or unsupported) |
| `NOT_ASSESSED` | Role not present or not evaluated for this asset | Hash primitive evaluating KEX role |

---

### 3. Hybrid Cryptography Axioms

1. **Axiom 1: Dependency != Actual Use**
   - Having `liboqs` in a virtual environment or `pom.xml` yields `library: PQC_CAPABLE`. It does NOT yield `PQC_NEGOTIATED` on any network endpoint.
2. **Axiom 2: Hybrid KEX != PQC Signature**
   - Negotiating `X25519MLKEM768` satisfies `key_establishment: HYBRID_NEGOTIATED`. The leaf certificate and TLS handshake signatures remain evaluated under `signature: CLASSICAL_ONLY` unless explicitly signed with ML-DSA / Falcon.
3. **Axiom 3: Supported != Negotiated**
   - An SSH server advertising PQC in KEXINIT is recorded as `PQC_ADVERTISED`. It is only `PQC_NEGOTIATED` if the client selected it and the KEX completed.
4. **Axiom 4: Scanner Failure is Never Negative Evidence**
   - If the network scanner fails or times out, the asset is tagged `SCANNER_UNAVAILABLE`, preserving audit integrity.
