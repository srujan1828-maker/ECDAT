# ECDAT V4 — P2.2 Agility Model & State Specification
## Dimensions, States, Confidence, and Scoring Semantics

### 1. Categorical Agility States

The platform represents agility as categorical states rather than opaque numerical scores. Each dimension evaluates to one of the following eight states:

| State | Semantic Definition | Migration Feasibility Implication |
| :--- | :--- | :--- |
| `SUPPORTED` | Proven architectural mechanism exists for dynamic algorithm substitution, rotation, or reload. | Seamless or runtime cryptographic transition possible. |
| `OBSERVED` | Concrete evidence observed demonstrating configuration-driven or modular behavior. | Straightforward migration requiring configuration or dependency update. |
| `PARTIALLY_OBSERVED`| Mixed signals: some modularity exists alongside constraints or unverified components. | Moderate migration complexity; partial code modifications required. |
| `CONSTRAINED` | Architectural friction detected: pinned dependencies, manual rotation, non-reloadable runtime. | Significant code, operational, or deployment changes required. |
| `BLOCKED` | Hard architectural or binary barrier: hardcoded primitives, embedded private keys, static ROM. | High friction; requires complete code rewrite, binary recompilation, or hardware replacement. |
| `UNKNOWN` | No relevant evidence collected for this dimension. | Cannot determine agility; further scanning or manual inspection needed. |
| `NOT_APPLICABLE` | Dimension does not apply to this asset type (e.g. Protocol Agility on an isolated algorithm definition). | Excluded from evaluation and composite derivations. |
| `SCANNER_UNAVAILABLE`| Evidence collection failed due to scanner errors, network timeouts, or missing dependencies. | Explicitly distinguishes tool failure from poor agility. |

---

### 2. Confidence Model

Confidence reflects the evidential strength backing the assessment, mapped strictly from P0 evidence levels ($E0$–$E5$) and fusion states:

| Agility Confidence | Backing Evidence Levels | Fusion State Requirements |
| :--- | :--- | :--- |
| `HIGH` | $E4$ (Dynamic Execution / AST Analysis) or $E5$ (Live Protocol Verification) | `MEASURED` or `CORROBORATED` |
| `MEDIUM` | $E3$ (Static Declarations, Lockfiles, Build manifests) | `MEASURED` or `INFERRED` |
| `LOW` | $E1$ / $E2$ (Symbol references, heuristic strings) | `INFERRED` or uncorroborated single source |
| `UNKNOWN` | $E0$ (Unverified claims, missing inputs) | `CONTRADICTORY` or no evidence |

### 3. Detailed Dimension Specifications

#### Dimension 1: Algorithm Agility (`ALGORITHM`)
- **Positive Evidence**: Provider abstraction API calls (`EVP_CIPHER_fetch`, `Cipher.getInstance`, `WebCrypto.subtle`, `BCryptOpenAlgorithmProvider`), dynamic algorithm factory patterns.
- **Negative Evidence**: Direct primitive function invocations (`DES_ede3_cbc_encrypt`, `AES_encrypt`, `MD5_Init`, `SHA1_Update`).
- **Rules**: `AGL-ALG-001` through `AGL-ALG-005`.

#### Dimension 2: Configuration Agility (`CONFIGURATION`)
- **Positive Evidence**: Dynamic environment variables (`os.getenv("CIPHER_SUITE")`), externalized configuration files (`crypto.conf`, `settings.yaml`), external secret manager integration.
- **Negative Evidence**: Hardcoded cryptographic keys, hardcoded IVs, static cipher parameters embedded in source code.
- **Rules**: `AGL-CFG-001` through `AGL-CFG-005`.

#### Dimension 3: Dependency Agility (`DEPENDENCY`)
- **Positive Evidence**: Dynamic shared libraries (`.so`, `.dll`, `.dylib`), modern package manager specifications with semantic version ranges (`>=3.0.0, <4.0.0`), pluggable engine architectures.
- **Negative Evidence**: Static in-tree vendored dependencies, exact immutable lockfile pinning with deprecated versions, compiled-in static cryptographic engines.
- **Rules**: `AGL-DEP-001` through `AGL-DEP-004`.

#### Dimension 4: Protocol Agility (`PROTOCOL`)
- **Positive Evidence**: Live dynamic protocol negotiation (TLS 1.2 & TLS 1.3), runtime cipher negotiation, configurable protocol order, dynamic SSH key exchange advertisement.
- **Negative Evidence**: Single fixed protocol configuration, hardcoded SSLv3/TLSv1.0 enforcement, rigid non-negotiable cipher suite lists.
- **Applicability**: Only evaluated for network endpoints, services, and protocol definitions. Marked `NOT_APPLICABLE` for standalone algorithms and data assets.
- **Rules**: `AGL-PRT-001` through `AGL-PRT-004`.

#### Dimension 5: Certificate / Key Agility (`CERTIFICATE_KEY`)
- **Positive Evidence**: Automated certificate rotation via ACME (`cert-manager`, `Let's Encrypt`), automated CRL/OCSP checking, external Hardware Security Module (HSM) or cloud KMS integration.
- **Negative Evidence**: Hardcoded private keys in source, embedded certificates in binary images, manual certificate file updates without automated renewal.
- **Rules**: `AGL-CRT-001` through `AGL-CRT-004`.

#### Dimension 6: Deployment Agility (`DEPLOYMENT`)
- **Positive Evidence**: Containerized deployment (`Dockerfile`, Kubernetes deployment), zero-downtime rolling restart, dynamic configuration reload without process restart (e.g. SIGHUP handler).
- **Negative Evidence**: Immutable bare-metal installations, read-only firmware ROM images, physical hardware appliance deployments.
- **Rules**: `AGL-DPL-001` through `AGL-DPL-004`.

#### Dimension 7: Validation Agility (`VALIDATION`)
- **Positive Evidence**: Automated cryptographic test suites, Known Answer Tests (KAT), Google Project Wycheproof vector execution, automated regression pipelines verifying algorithm substitution.
- **Negative Evidence**: Explicit absence of test coverage (`no_tests_observed`), missing cryptographic test harnesses.
- **Rules**: `AGL-VAL-001` through `AGL-VAL-003`.

### 4. Derived Composite Score Semantics

To satisfy legacy reporting and high-level dashboards while preserving scientific integrity, the engine calculates a **derived composite score**:

$$\text{Composite Score} = \frac{1}{|D_{\text{applicable, known}}|} \sum_{d \in D_{\text{applicable, known}}} \omega(\text{State}_d)$$

Where standard categorical weights $\omega(\cdot)$ are:
- `SUPPORTED`: $1.0$
- `OBSERVED`: $0.8$
- `PARTIALLY_OBSERVED`: $0.5$
- `CONSTRAINED`: $0.3$
- `BLOCKED`: $0.0$

**Strict Guardrails**:
1. Dimensions evaluated as `UNKNOWN`, `NOT_APPLICABLE`, or `SCANNER_UNAVAILABLE` are **completely excluded** from both the numerator and denominator.
2. If all dimensions are unknown or not applicable, `composite_score` evaluates to `None` / `0.0`.
3. The API response explicitly annotates:
   ```json
   "composite_score": 0.75,
   "score_type": "DERIVED",
   "score_disclaimer": "Derived unweighted mean over applicable, known dimensions. Categorical states are the primary source of truth."
   ```
